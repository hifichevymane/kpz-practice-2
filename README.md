# Практичне заняття №2

## Комплексне дослідження структури, конфігурацій та робочого середовища сучасного JavaScript-проєкту на основі бойлерплейта vite-react-boilerplate

**Мета:**
Познайомитись із структурою файлу package.json як центрального конфігураційного файлу JavaScript-проєкту, зрозуміти основні поля: імʼя, автор, опис, версія, ліцензія, репозиторій, скрипти та залежності.
Вивчити принципи семантичного версіонування (SemVer) через аналіз реальних залежностей.
Ознайомитись із практикою оформлення проєктної документації (README.md).
Вивчити призначення файлів .gitignore та LICENSE.
Розібратися з роботою гіт-хуків через аналіз артефактів, які створює бібліотека Husky.

2. Аналіз структури файлу package.json
  - Опишіть у звіті призначення полів файлу package.json: name, author, description, version, license, repository, scripts, dependencies, devDependencies.
  - Проаналізуйте залежності, вказані у dependencies та devDependencies, поясніть логіку такої класифікації.

**Відповідь:**

*Призначення основних полів у package.json*

  -	name — назва пакета. Вказує, як проєкт ідентифікується в системі пакетів. У цьому випадку — vite-react-boilerplate.
  -	author — ім’я автора або команди, яка створила проєкт. Тут зазначено: Ricardo Valdovinos.
  -	description — короткий опис проєкту, що пояснює його призначення. Наприклад, “стартер шаблон для проєктів на Vite + React”.
  -	version — версія проєкту, яка використовується для контролю релізів. Дотримується стандарту SemVer (Semantic Versioning), наприклад, 1.0.0.
  -	license — тип ліцензії, який регулює права на використання проєкту. У цьому випадку — MIT, що є відкритою ліцензією.
  -	repository — посилання на репозиторій Git, де зберігається код. Поле містить тип системи контролю версій (git) і URL репозиторію.
  -	scripts — набір команд, які можна запускати через npm run. Скрипти використовуються для запуску сервера, тестів, збірки, форматування, ініціалізації husky тощо.
  -	dependencies — список бібліотек, які потрібні безпосередньо для роботи додатку в production. Це бібліотеки, що імпортуються у коді програми.
  -	devDependencies — список бібліотек, які потрібні лише на етапі розробки. Наприклад: інструменти для лінтингу, тестування, форматування, документації.

**dependencies і devDependencies**

*Залежності в dependencies:*

  - Містять основні бібліотеки для роботи користувацького інтерфейсу: react, react-dom, zustand, react-hook-form.
  - Містять інструменти для обробки форм та валідації: @hookform/resolvers, zod.
  - Використовуються для побудови діаграм: @nivo/bar, @nivo/line, @nivo/pie.
  - Забезпечують локалізацію: i18next, react-i18next, i18next-browser-languagedetector, i18next-http-backend.
  - Для обробки дат: dayjs.
  - Для роботи з даними, таблицями та маршрутизацією: @tanstack/react-query, @tanstack/react-table, @tanstack/react-router.

Ці бібліотеки використовуються у вихідному коді додатку та будуть включені у фінальну збірку для продакшена.

*Залежності в devDependencies:*

  - Містять лінтери та плагіни: eslint, eslint-plugin-react, @typescript-eslint/*, eslint-config-prettier, eslint-plugin-unicorn тощо.
  - Інструменти для форматування коду: prettier.
  - Типи для TypeScript: @types/react, @types/node, @types/react-dom, тощо.
  - Інструменти для тестування: vitest, @vitest/coverage-v8, @testing-library/react, @playwright/test.
  - Пакети для Storybook: @storybook/*, які дозволяють створювати та переглядати ізольовані UI-компоненти.
  - Допоміжні пакети для комітів: husky, @commitlint/*, commitizen, cz-conventional-changelog.
  - Інструменти для CSS: tailwindcss, autoprefixer, postcss.
  - Інші утиліти для розробки: shx, jsdom, vite, vite-plugin-static-copy.
   
Ці залежності не використовуються напряму у production-коді, і їх призначення — полегшити, автоматизувати або стандартизувати процес розробки.

Логіка поділу:

  - Все, що потрібне для запуску додатку у продакшені (тобто потрапляє у фінальну збірку) — зберігається в dependencies.
  - Все, що потрібне лише розробнику — для перевірки коду, форматування, тестування, комітів, генерації документації — зберігається в devDependencies.

3. Семантичне версіонування (SemVer)
  - Ознайомтесь із принципами SemVer.
  - Дослідіть версії пакетів бойлерплейту. Поясніть, які оновлення (мажорні, мінорні, патчі) допускаються відповідно до версій, зазначених у файлі package.json.

SemVer — це стандарт версіонування, який описується у форматі:
MAJOR.MINOR.PATCH

Розшифровка:

  1.	MAJOR (мажорна версія) — несумісні зміни.
  Наприклад: 1.0.0 → 2.0.0 означає, що API або поведінка змінились і можуть зламати старий код.
  2.	MINOR (мінорна версія) — нові функції, але без порушення сумісності.
  Наприклад: 1.0.0 → 1.1.0.
  3.	PATCH (патч-версія) — виправлення помилок, не впливаючи на API.
  Наприклад: 1.0.0 → 1.0.1.

У більшості залежностей у файлі зазначено формат на кшталт:

"назва-пакета": "^x.y.z"

Символ ^ — означає, що дозволені оновлення мінорних і патч-версій, але не мажорних.

Наприклад:

  - "react": "^18.3.1": Дозволені оновлення до 18.x.x, наприклад 18.4.0, 18.3.2, але не 19.0.0.
	- "zod": "^3.23.8": Дозволені оновлення до 3.x.x, але не 4.0.0.
	- "@playwright/test": "^1.46.1": Дозволені оновлення до будь-яких 1.x.x, але не 2.0.0.


Які оновлення допускаються?

З ^x.y.z допускаються:
- Мінорні оновлення (наприклад, 3.23.8 → 3.24.0)
- Патчі (наприклад, 3.23.8 → 3.23.9)
- Не допускаються мажорні (наприклад, 3.23.8 ✘ 4.0.0)
Це дозволяє:
- Автоматично отримувати нові фічі та виправлення помилок.
- Уникати автоматичного оновлення до потенційно небезпечних змін, які ламають сумісність.

**4. Дослідження додаткових конфігураційних файлів**
  - Проаналізуйте та опишіть призначення, структуру та важливі елементи файлів:
  - README.md
  - .gitignore
  - LICENSE

Відповідь:

**README.md**

Призначення:
Файл для опису проєкту — перше, що бачить користувач на GitHub. Допомагає зрозуміти мету, структуру, інструкції.

Структура та важливі елементи:
- Назва проєкту
- Короткий опис
- Інструкції з установки та запуску
- Приклади використання
- Посилання на документацію
- Ліцензія


**.gitignore**

Призначення:
Визначає файли та папки, які Git має ігнорувати — не додавати до репозиторію.

Важливі елементи:
- node_modules/ — зовнішні залежності
- dist/, build/ — результати збірки
- .env, *.log, *.lock — конфіденційні або тимчасові файли


**LICENSE**

Призначення:
Юридичний документ, що визначає умови використання проєкту третіми особами.

Структура (на прикладі MIT):
- Дозвіл на використання, копіювання, зміну, розповсюдження
- Відмова від відповідальності
- Умови включення ліцензії у всі копії ПЗ

5. Аналіз роботи гіт-хуків Husky

Дослідіть артефакти, які створюються після встановлення та налаштування бібліотеки Husky.
Опишіть, для чого потрібні ці артефакти, як вони налаштовуються та яку роль відіграють у процесі розробки.

Відповідь:

Husky — інструмент для підключення Git-хуків, який дозволяє запускати команди (наприклад, лінтинг або тести) перед комітом чи пушем.

Після встановлення створюються:
- Папка .husky/ — містить скрипти-хуки (pre-commit, pre-push тощо).
- Файли-хуки — виконують задані команди (наприклад, npm test).
- Скрипт prepare у package.json — активує хуки після npm install.

Призначення артефактів:
- Автоматизація перевірок перед комітом.
- Захист репозиторію від неякісного коду.
- Єдині правила для всієї команди.

Husky допомагає підтримувати чистоту та якість коду автоматично під час розробки.
